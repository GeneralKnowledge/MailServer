## 3. Domain and DNS considerations

To be filled from the script's DNS section once the domain is known. Points
to check:

- **Existing MX.** If the domain already receives mail elsewhere (Google
  Workspace, Microsoft 365, registrar forwarding), switching MX moves **all**
  of the domain's incoming mail to mailcow. Existing addresses would stop
  receiving at the old provider. Options: (a) migrate those mailboxes first,
  (b) use a subdomain for this service (e.g. `@m.example.com`), or (c) keep the
  old MX until cut-over. **No MX change before the operator confirms.**
- **Existing SPF.** There can be only one SPF TXT record. If one exists, add
  `mx` (or `ip4:<server IP>`) to it rather than adding a second record.
- **Existing DMARC.** Keep the policy; start new ones at `p=none` with `rua`
  reporting, tighten to `quarantine` after deliverability tests pass.
- **Websites.** Only `mail.<domain>`, `autodiscover.<domain>`,
  `autoconfig.<domain>`, MX, TXT and SRV records are added. The apex and `www`
  records are untouched.
- **CAA.** If a CAA record exists, it must allow `letsencrypt.org`.
- **Cloudflare (if used).** `mail.`, `autodiscover.` and `autoconfig.` must
  be **DNS-only (grey cloud)**; proxied records break SMTP/IMAP and ACME.

Records that will be created in M2 (values filled in then):

| Name | Type | Value |
|---|---|---|
| `mail` | A | server's reserved IPv4 |
| `@` | MX 10 | `mail.<domain>` |
| `@` | TXT | `v=spf1 mx -all` (merged with any existing SPF) |
| `dkim._domainkey` | TXT | generated by mailcow |
| `_dmarc` | TXT | `v=DMARC1; p=none; rua=mailto:postmaster@<domain>` |
| `autodiscover`, `autoconfig` | CNAME | `mail.<domain>` |
| `_autodiscover._tcp` | SRV | `0 1 443 mail.<domain>` |
| PTR (at Oracle) | PTR | `mail.<domain>` |

## 4. SMTP restrictions (the main risk)

**Outbound port 25.** Oracle's release note
["Outbound SMTP is blocked"](https://docs.oracle.com/en-us/iaas/releasenotes/changes/f7e95770-9844-43db-916c-6ccbaf2cfe24)
says tenancies created after 23 June 2021 cannot send on TCP 25 to the
internet, and that you "open a service limits request to request an
exemption". It is widely reported (not confirmed in Oracle's docs) that
**Always Free–only accounts are refused** and the account must be upgraded to
Pay As You Go. The script tests this directly with a real SMTP banner from
Gmail's and Outlook's MX hosts.

Without port 25 the server can still **receive** mail (inbound 25 is
controlled by the security list) but cannot **send** to other providers.

Options, in order of preference:

1. **Ask Oracle for the exemption** (service limits request). Free, keeps the
   architecture simplest. Upgrade to Pay As You Go first if the tenancy is
   Free Tier; Always Free resources remain free after upgrading.
2. **SMTP relay on port 587** via mailcow's built-in sender-dependent
   transport (no extra service). Candidates: OCI Email Delivery (same
   provider, priced per message, needs approved senders), or a third-party
   relay (Brevo, Mailgun, SMTP2GO, Amazon SES). DKIM is still signed by
   mailcow, but SPF must include the relay.

The design keeps both paths open: switching between them is a mailcow
setting, not a re-deployment.

**Reverse DNS.** Per
[OCI Reverse DNS (PTR)](https://docs.oracle.com/en-us/iaas/Content/Network/Concepts/reverse_dns.htm),
PTR records are set by service request after an A record for the FQDN exists
and matches the IP. Gmail and Outlook heavily penalise senders without a
matching PTR. Requires the A record `mail.<domain>` first, so this happens
early in M1. (With a relay, the relay's PTR is what counts, but a correct PTR
is still good practice.)

## 5. Network and firewall requirements

**OCI ingress (security list / NSG), TCP from 0.0.0.0/0:**

| Port | Use | Needed |
|---|---|---|
| 22 | SSH | Yes (restrict to admin IPs if possible) |
| 25 | SMTP inbound | Yes |
| 80 | ACME HTTP-01, redirect to HTTPS | Yes |
| 443 | SOGo, admin UI, autodiscover, registration app | Yes |
| 465, 587 | Client submission | Yes |
| 993 | IMAPS | Yes |
| 4190 | ManageSieve (filters) | Optional |
| 143, 110, 995 | IMAP/POP3 | Optional; recommend leaving closed (or 143 only if a client needs STARTTLS) |

**Host firewall.** Oracle's Ubuntu images ship `iptables-persistent` rules
(`/etc/iptables/rules.v4`) that REJECT everything but SSH in the INPUT chain.
mailcow's published ports go through Docker's FORWARD/DOCKER-USER chains, so
these INPUT rules usually do not block them, but the image's FORWARD REJECT
rule can. mailcow advises against `ufw`/`firewalld`. Plan: inspect the rules
(script does this), keep SSH-only INPUT, and leave Docker port handling to
Docker. The OCI security list is the primary firewall.

**Outbound:** 443 (Docker Hub, GitHub, Let's Encrypt), 53 TCP/UDP (mailcow's
own Unbound resolver), 25 (or 587 to a relay).

**MTU.** OCI VNICs normally use MTU 9000 or 1500; if the script reports
something else, mailcow's Docker network MTU may need adjusting.

**IPv6.** If the instance has no IPv6, disable IPv6 on mailcow's network (as
documented by mailcow) to avoid delivery attempts over a dead route.

## 6. Recommended deployment configuration

- mailcow-dockerized, official install, in `/opt/mailcow-dockerized`,
  pinned to the latest tagged release at install time.
- `MAILCOW_HOSTNAME=mail.<domain>`, mailcow's own nginx on 80/443 and
  mailcow's built-in ACME (Let's Encrypt). **No Caddy**: nothing else needs
  a proxy except the registration app, which mailcow's nginx can serve via a
  custom site config (or a separate subdomain) in M3.
- ClamAV and full-text search **on** (12 GB is enough). Turn off if RAM gets
  tight (`SKIP_CLAMD=y`, `SKIP_FTS=y`).
- 2 GiB swap file on the host.
- Time zone `Europe/London`.
- Registration app (M3): separate Docker Compose project, outside the mailcow
  directory, SQLite, talking to mailcow's API over HTTPS with an
  IP-allow-listed key.

## 7. Compatibility issues to watch

- **ARM64:** officially supported. Any image without an arm64 build will show
  up at `docker compose pull`; checked in M1 before `up`.
- **mailcow API keys are not fine-grained.** mailcow offers read-only and
  read-write keys; a read-write key has full admin API rights. Mitigations:
  allow-list the key to the registration app's source IP, keep it server-side
  only, and have the app call only the mailbox endpoints. This is the closest
  mailcow gets to "restricted credentials"; noted for the security review.
- **Oracle idle-instance reclamation:** Always Free instances with very low
  CPU use can be reclaimed. A mail server usually stays above the threshold,
  and upgrading to Pay As You Go (likely needed for port 25 anyway) removes
  this risk.
- **Signup extension:** evaluated and **not recommended**; see
  [signup-extension-evaluation.md](signup-extension-evaluation.md).
